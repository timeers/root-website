{% load i18n %} {% comment %} A 7-or-8-column weekly availability grid, shared by the /availability settings page and WEEKLY_AVAILABILITY survey questions. Lives at the project level because both the_gatehouse and the_tavern include it -- putting it in either app's template dir would make the dependency direction arbitrary. The behaviour comes from the_keep/static/the_keep/availability_grid.js, which auto-initialises anything with .js-availability-grid. Everything it needs is carried on the grid element itself, so several grids can sit on one page. Parameters: grid_id unique DOM id for this grid (required when there are several) field_id id of the hidden input the selection serializes into count_id optional id of a badge showing how many hours are selected clear_id optional id of a "clear all" button days DAY_LABELS from the_gatehouse.services.availability -- used when `hour_rows` is absent (the dateless 7-day case: the general row, and every WEEKLY_AVAILABILITY survey grid). data-how is NOT rendered here; availability_grid.js derives it client-side as day*24+hour, exactly as before. hours hour_labels() -> (hour, short_label, long_label) triples editable adds the editor affordances (hover, cursor, selected colour) columns OPTIONAL. A week-specific (real-dated) grid's column list -- each item a dict with `header_label` (e.g. "Mon"), `header_sublabel` (e.g. "9/14/26", rendered as a second line) and `header_title` (full accessible title). Supplies ONLY the header row; see `hour_rows` for the cell grid. hour_rows OPTIONAL, required alongside `columns`. Pre-assembled by the view as one entry per hour_labels() row: (hour, short_label, long_label, cells), where `cells` has exactly len(columns) entries in column order, each a LIST of 0/1/2 (utc_how, is_preview) pairs for that (column, hour) position -- see services.availability.week_grid_cells for why it's a list, not a single value (DST fall-back/spring-forward). Pre-assembled server-side because Django templates cannot index a list by a loop variable, so nesting two independent `{% for %}` loops (columns x hours) to look up a cell can't work here the way the dateless case's day*24+hour can -- same reason each pair is pre-zipped rather than kept as two parallel lists. Cells carry a server-rendered `data-how` in columns-mode (a real hour-of-week int) so the JS never needs to know it's looking at a real UTC week's non-contiguous encoding rather than the dateless 7-day one -- see availability_grid.js. A (column, hour) slot with 0 UTC hours (the DST spring-forward gap, or simply outside a partial boundary column) renders one DISABLED cell with no data-how; a slot with 2 (the DST fall-back repeat) renders two half-width cells side by side, each its own data-how. `is_preview` marks a cell whose hour is implied by the general/standing pattern but not yet saved for this specific week -- rendered as a faint diagonal-stripe backdrop (avail-cell--general-preview), fully clickable like any other empty cell. {% endcomment %}
