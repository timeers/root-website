Fix permanently-stuck guilds_refreshing logins
==============================================

REVISION NOTE (this pass)
Changes 1, 2 and 3 are already implemented on the lfg-improvements branch. Changes 4, 5
and the read-half of Change 1 are not, and the branch is currently in a BROKEN
intermediate state — see "Current state" and Change 0 below. This revision:
  * adds Change 0, a live bug the half-landed work introduced (must fix first);
  * pins down the call-site contract the original plan left implicit (the cause of that
    bug);
  * gives the NO_TOKEN report an actual home and a spam cap;
  * makes the staleness window track liveness instead of total elapsed time;
  * aligns the poller cap with GUILDS_REFRESH_MAX_AGE instead of the retry ladder;
  * corrects the test instructions to the names/types that actually shipped.

Context
Users report being stranded forever on the "Finishing your sign-in" spinner, or (for
groups E/P) carrying a permanent header avatar spinner plus an every-2s XHR on every
page. Root cause: Profile.guilds_refreshing is set to True on every login but is cleared
by only three narrow code paths, none of them fail-closed. Once the flag sticks, nothing
in the system ever retries or expires it — there is no timeout, no attempt cap, no
sweep, and no admin lever.

Four independent ways a profile gets stranded today:
1. A permanent failure routed through a transient-retry path (the main cause).
   get_valid_discord_token (discordservice.py:1071-1120) returns None when there is no
   SocialToken row, or the token is expired with an empty token_secret. get_user_guilds
   then returns None, refresh_user_guilds returns False writing nothing, and the task
   burns 4 attempts over ~180s. Any worker restart, deploy, or dropped broker message
   inside that window strands the profile permanently.
2. Early return with no cleanup. tasks.py:430-432 — if user is None or not
   hasattr(user, 'profile'): return, a bare return that leaves the flag up.
3. Dead broker at enqueue time. signals.py:289 enqueues inside transaction.on_commit.
   The flag is committed True first; the callback then runs post-commit and .delay()
   raises kombu.exceptions.OperationalError if Redis is down — stranding every user who
   logs in during the outage, and letting the exception escape into the login response.
4. No fail-closed cleanup. refresh_user_guilds (tasks.py:317-411) clears only on its
   success path; both return False sites write nothing. That's correct for the helper,
   but neither caller compensates.

Why E/P users are affected. Profile.player (models.py:1259-1265) is True for A/D/E/P, so
player_required never bounces them — they pass the check and never see the hold page.
Their symptom is the permanent avatar spinner (rendered twice, header.html:80,93) and
unbounded polling. The users who actually land on "Finishing your sign-in" are stuck
group O users, via _not_a_player_redirect (views.py:268-280).

Auth model — verified, and it shapes the fix. Login is Discord OAuth via allauth, so in
the normal case every user does have a Discord token, and _store_token()
(allauth/socialaccount/models.py:362-383) upserts it on every login
(SOCIALACCOUNT_STORE_TOKENS = True, settings.py:310). A missing token is therefore an
error condition to control for, not a user-facing state. Three verified ways it still
arises:
1. Non-Discord logins are reachable. SOCIALACCOUNT_ONLY is commented out
   (settings.py:312) and urls.py:77 includes all of allauth.urls, exposing
   account_login/account_signup (account/urls.py:11,19); ACCOUNT_SIGNUP_FIELDS includes
   password fields (settings.py:305) and ModelBackend is first in
   AUTHENTICATION_BACKENDS (settings.py:124-130). Django admin at urls.py:36 is exactly
   this path — every superuser login fires user_logged_in with no SocialAccount, hitting
   the "No Discord social account" branch (discordservice.py:1079-1082) and, today,
   burning the full 180s retry chain.
2. prompt: 'none' (settings.py:157-163) skips the consent screen — correct for UX, but
   if a user revoked the app's authorization on Discord's side, the OAuth round trip
   errors rather than re-consenting, so a re-login does not silently repair them.
3. Discord doesn't always resend a refresh token — allauth only overwrites token_secret
   when non-empty (models.py:373-376), and discordservice.py:1091-1093 returns None for
   an expired token with no token_secret. A token can be present-but-unusable.

So the token check below exists purely to classify retries and surface the error, not to
drive any user-facing flow.

Intended outcome: a stuck flag becomes impossible to sustain — it expires on read, every
terminal task path clears it, a broker outage can't strand anyone, and the flag is only
ever raised when a sync the user actually needs is in flight.

Out of scope (user's call): production users were already unstuck by hand, so no
management command, admin action, or periodic sweep task. The staleness window below is
the durable safety net.

Change 0 — Fix the live truthiness bug (do this FIRST, it ships alone)
The original plan said the enum and its call sites "must land in the same commit or
logins break." The enum landed; the call sites did not. The result is a live bug on the
branch.

signals.py:278 assigns a GuildSyncResult into `synced_inline`, which is then tested at
signals.py:284 as `if not synced_inline:`. GuildSyncResult subclasses str, so EVERY
member — including TRANSIENT and NO_TOKEN — is truthy. `not synced_inline` is therefore
always False and the fallback enqueue NEVER fires. A user whose inline sync fails now
gets no async retry at all, and (because signals still never stamps
guilds_refresh_started_at) a flag that the new property reads as instantly stale.

Two edits, both required:

(a) Drop `str` from the enum base at tasks.py:319:

    class GuildSyncResult(Enum):

Verified safe: the enum never crosses a serialization boundary. Its only producer is
refresh_user_guilds and its only consumers are tasks.py:478 and signals.py:278;
refresh_user_guilds_task returns None on every path, so no Celery result carries it.
Keeping `str` is what let a wrong comparison pass silently instead of raising — with
plain Enum, `if not result` on an Enum member is still legal Python but the value can no
longer masquerade as its string, and the identity comparisons below become the only
correct way to read it.

(b) Compare by identity at the call site. See the contract immediately below.

CALL-SITE CONTRACT (the thing the original plan left implicit — state it, don't infer it)
refresh_user_guilds returns a GuildSyncResult, never a bool. Both call sites MUST test
it by identity against a named member. Never truth-test the result, never `==` it
against a string, and never store it in a variable whose name implies a bool.

  * signals.py — `synced_inline = refresh_user_guilds(...)` becomes:
        result = refresh_user_guilds(user, budget=INLINE_GUILD_SYNC_BUDGET)
        ...
        if result is not GuildSyncResult.OK:   # hand off to Celery
    with `result = None` as the "didn't try" initial value, so the not-OK branch covers
    both "no attempt" and "attempt failed" exactly as the old `synced_inline = False` did.
  * tasks.py:488-497 — already correct (`is GuildSyncResult.OK`, `is GuildSyncResult.NO_TOKEN`).

signals.py must import GuildSyncResult alongside the existing refresh_user_guilds import
at signals.py:23.

REVISION — keep the window tracking liveness, not total elapsed time.
GUILDS_REFRESH_MAX_AGE is justified as "~180s of retries plus queue latency", but
tasks.py:503 retries with countdown=30*(retries+1): 30+60+90 = 180s of backoff alone,
before execution time. The window and the retry ladder are two independent constants that
silently overlap, and if max_retries is ever raised the ladder outruns the window — the
spinner vanishes while a retry is genuinely still queued, which is the exact contract
tasks.py:460-463 promises to preserve.

Fix: re-stamp the timestamp before each retry, so the window measures "time since the
last sign of life" rather than "time since login":

    profile = user.profile
    profile.guilds_refresh_started_at = timezone.now()
    profile.save(update_fields=['guilds_refresh_started_at'])
    raise self.retry(countdown=30 * (self.request.retries + 1))

This makes GUILDS_REFRESH_MAX_AGE independent of the retry configuration: it now only
has to exceed the longest single gap between attempts (90s worst case), which 5 minutes
comfortably does. Add a comment at the constant saying so, replacing the "~180s of
retries" rationale, which no longer holds.


Change 2 — Classify transient vs. no-token failure  [predicate + enum DONE, report TODO]
Shipped: discord_refresh_capability (discordservice.py:1071), the GuildSyncResult enum,

get_user_guilds signatures were untouched, so their other callers (the add-guild-from-

REVISION — the report has no home, and needs a spam cap.
The original plan said a NO_TOKEN outcome for a user who DOES have a Discord
SocialAccount should logger.warning and send a category='report' message, suppressed
when there's no SocialAccount at all. That never landed, and as written it cannot:
refresh_user_guilds collapses 'no_account' and 'no_token' into the single
GuildSyncResult.NO_TOKEN (tasks.py:371-372), discarding the exact distinction the
predicate was built to preserve. Neither caller can tell them apart. tasks.py contains no
category='report' send at all.

Fix: report at the point that still has the string — inside refresh_user_guilds, where
the predicate is called. Do NOT widen the enum; the callers genuinely don't need a third
member (both treat any no-token outcome identically: clear and stop).

    capability = discord_refresh_capability(user)
    if capability != 'ok':
        if capability == 'no_token':
            # Has a Discord account but no usable token: a real fault, and invisible
            # until someone reports a stuck spinner. 'no_account' is the ordinary
            # admin/password login and is NOT a fault, so it stays silent.
            logger.warning("Discord token unusable for %s; skipping guild refresh", user)
            _report_unusable_token(user)
        return GuildSyncResult.NO_TOKEN

Spam cap. A user with a revoked token re-logs in repeatedly, and each login would fire a
report. Gate it on a short-lived cache key so a broken account reports at most once a day:

    def _report_unusable_token(user):
        """One report per user per day: a revoked token re-reports on every login, and
        an alert that repeats is an alert that gets muted."""
        key = f'unusable-discord-token:{user.pk}'
        if cache.add(key, True, timeout=60 * 60 * 24):
            send_discord_message_task.delay(
                f"No usable Discord token for {user} — guild refresh skipped. "
                f"They should log out and back in via Discord.", category='report')

cache.add is atomic and returns False when the key exists, so concurrent logins send
once. tasks.py has no `cache` import yet; add `from django.core.cache import cache`
(signals.py:7 is the existing precedent).

Note the tasks.py:492 branch in refresh_user_guilds_task already logger.warning's
NO_TOKEN. Leave it — it names the task context, and the report now fires one level down.

Login-safety audit
Reviewed specifically for anything that could break or change how users log in.

Errors found and corrected in this plan:
1. Enum truthiness — see Change 0. GuildSyncResult subclassing str made every member
   truthy, so `if not synced_inline` silently disabled the async fallback. This is what
   the original plan's "must land in the same commit" warning was pointing at, but it
   never said what the new comparison should BE. Now pinned in the call-site contract.
2. Empty update_fields silently skips the save — see the constraint in Change 4. Was a
   real data-loss path for discord_id; now guarded.
3. property name vs. update_fields — guilds_refresh_in_progress is a @property, so it
   must never appear in an update_fields list. Only the two concrete fields
   (guilds_refreshing, guilds_refresh_started_at) may. Django raises ValueError for
   non-concrete names (base.py:869-875) — that would 500 the login, so this is worth a
   careful read at each of the three call sites.
4. except Retry: raise ordering — if a broad except Exception is placed before it, Retry
   (a subclass of Exception) gets swallowed and the retry silently becomes a terminal
   clear. The Retry branch must come first. (Already correct at tasks.py:479.)
5. Staleness window vs. retry ladder — two independent constants that could drift into
   contradiction. Change 1's re-stamp decouples them.

Verified as NOT breaking login:
  * Only one user_logged_in receiver exists (signals.py:225) — confirmed by grep across
    the app. No second handler races the flag.
  * The signal is wrapped so Discord failures can't break login (signals.py:277-282) —
    the existing try/except stays; Change 2's predicate is a DB read, not a network call,
    and runs inside it.
  * profile_guilds_status has no @login_required (views.py:2199, urls.py:30) and relies
    on getattr(request.user, 'profile', None) returning None for AnonymousUser. Switching
    line 2209 to the property must keep the `profile is None` check first, or an
    anonymous poll raises AttributeError. Preserve the existing short-circuit exactly.
  * transaction.on_commit still fires under TestCase only inside
    captureOnCommitCallbacks; existing tests already account for this (tests.py:9365), so
    Change 4(b)'s wrapper doesn't alter test semantics.
  * No migration backfill runs against the users table, so the deploy is a pure additive
    AddField — no lock of consequence, no login downtime. (Already deployed as 0042.)
  * The report send in Change 2 is send_discord_message_task.delay — itself a broker
    call, and therefore itself able to raise OperationalError during an outage. It runs
    inside refresh_user_guilds, which the login handler already wraps in try/except
    (signals.py:279-282), so a broker outage during a no-token login still cannot break
    login. Confirm this stays true if the report is ever moved.

Behavior changes users will actually notice (intended, but call out in the PR):
  * Returning A/D/E/P players: the header spinner and the every-2s poll disappear, and
    there is no longer a full page reload mid-session when the background sync lands.
    Login itself is unchanged and slightly lighter.
  * REVISION — the flip side of that, which the original plan omitted: a returning player
    who was DEMOTED on Discord (left the guild) now renders the entire session against
    the stale cached group, with no mid-session reload to correct it. Their next login
    catches it. This is an accepted trade — the alternative is the spinner-for-everyone
    behavior being removed — but it is a real behavior change and belongs in the PR notes
    rather than being discovered later.
  * First-login and group-O users: unchanged happy path (inline sync under the 6s budget,
    spinner only if it doesn't finish).
  * Admin/password logins: no longer set a flag or enqueue a doomed task. Previously this
    silently burned a 180s retry chain per admin login.

Explicitly unchanged: the OAuth flow, INLINE_GUILD_SYNC_BUDGET = 6 (signals.py:40), the
needs_sync_now predicate itself, group-promotion logic, the admin-group sync at
signals.py:302-328, and the "Continue anyway" escape hatch.

Deviations made during implementation (plan updated to match the code as shipped)
1. can_refresh is evaluated for EVERY login, not only when needs_sync_now. The plan's
   phrasing ("keep it inside the needs_sync_now branch so the common path pays nothing")
   would have skipped the enqueue for returning A/D/E/P players entirely -- they are
   supposed to keep the silent background refresh. The predicate now gates the flag
   (with needs_sync_now) and the enqueue (alone), costing two indexed queries on every
   login. That is the real price of not enqueueing doomed work; the comment at
   signals.py says so rather than claiming it is free.
2. The orphan-cleanup branch in refresh_user_guilds_task is narrower than the original
   plan implied. Profile.user is on_delete=SET_NULL (models.py:1017), so DELETING a user
   nulls profile.user_id and Profile.objects.filter(user_id=user_id) finds nothing -- the
   lookup cannot reach a truly orphaned profile. Those rows are freed by the staleness
   window instead. The branch still covers the reachable case (the row points at a user
   the task failed to load) and is kept, with a comment saying which case is which, plus
   a test documenting the SET_NULL behavior so the branch isn't mistaken for the fix.
3. Test patch targets differ by call site, and this is easy to get wrong: signals.py
   imports discord_refresh_capability at MODULE level (signals.py:22), so tests patch
   'the_gatehouse.signals.discord_refresh_capability'; refresh_user_guilds imports it
   INSIDE the function, so that one is patched on
   'the_gatehouse.services.discordservice.discord_refresh_capability'. Tests exercising
   a full login through to the inline refresh need BOTH.
4. Staging a retries-exhausted state uses task.push_request(retries=...) /
   task.pop_request(). Task.request is a read-only property backed by a stack, so
   mock.patch.object(task, 'request') raises AttributeError.
